# Room Agent 仕様書 — 画像/動画から室内空間を構造化し、模様替え案を生成するAIエージェント

- 作成日: 2026-11-01
- 状態: ドラフト(レビュー待ち)
- 対象リポジトリ: `taiguijize-droid/test`(現時点でコードなし。本仕様が最初の成果物)
- 発端となった会話の要点:
  - 相場チャート1枚を読むように、部屋を「読んで」分析したい
  - 1枚の写真では部屋全体が写らないので、複数枚の画像または動画から部屋全体を把握したい
  - 3Dは今は不要。室内空間を「構造」として作れればよい
  - 映っている物をAIが把握できるように、フォルダ構造のように階層化したい
  - 元々の部屋の大きさ(器)を、中身(家具・物)から分離したい
  - その上で、部屋の模様替え(家具の配置替え)案を生成するAIエージェントにしたい
  - まず「どこまでできるか」を確かめたい

---

## Problem Statement(課題)

部屋の写真を1枚撮ってAIに見せても、部屋の一部しか写っておらず、「部屋全体として何がどこにあるか」は分からない。複数枚撮っても、人間が頭の中で合成するしかなく、AIは枚数分の個別の説明を返すだけになる。

その結果、次のことができない。

- 部屋の中にある物を、場所ごとに整理された一覧として把握すること
- 部屋そのものの大きさ(壁・床・ドア・窓)と、中に置かれている家具・物を分けて考えること
- 「この部屋で、この家具を、どう置き直せるか」をAIに考えさせること

さらに、写真から部屋の寸法を当てることにどれだけ精度があるのか、小物をどこまで拾えるのか、模様替え案が物理的に成立するのか、といった「現在のVLMでどこまでできるか」が分からないまま大きく作り始めるのは危険である。

## Solution(解決策)

コマンドラインから動く「Room Agent」を作る。利用者は、1つの部屋を撮った写真のフォルダ、または1本の動画を渡す。エージェントは次を返す。

1. **部屋の器(Room Shell)**: 部屋の幅・奥行き・天井高の推定値、ドアと窓の位置。中身とは独立したデータとして保存する。推定が外れていたら利用者が数値で上書きできる。
2. **部屋ツリー(Room Tree)**: 部屋 → エリア → 家具 → 物、というフォルダのような階層。各ノードに、名前、種類、おおよその大きさ、どの写真に写っていたか、確信度を持たせる。複数の写真に写った同じ物は1つに統合する。
3. **配置(Layout)**: 器の上にマス目(グリッド)を敷き、家具の足元の占める範囲と向きを記録する。これが「3Dではない室内空間」の実体である。
4. **見える形での出力**: 真上から見た2D間取り図(SVG)、ツリーをそのまま実フォルダとして書き出したディレクトリ、そして「何が分かり、何が分からなかったか」をまとめた所見レポート。
5. **模様替え案(Rearrangement Proposal)**: 利用者の目的(例:「作業スペースを広く」)と、動かしたくない家具の指定を受けて、複数の配置案を生成する。各案は、はみ出し・重なり・ドアの塞ぎ・通路の確保をプログラムで検証済みで、理由と移動手順と2D図が付く。

VLM(視覚言語モデル)はAnthropicのClaude APIを使う。写真はAnthropic以外には送らない。

最初の成果物はCLIとライブラリ。Web画面やiPhoneアプリは、この仕様で「どこまでできるか」が見えてから別仕様で扱う。

## User Stories(ユーザーストーリー)

**取り込み**

1. 住人として、部屋の写真が入ったフォルダを1つ渡すだけで、写真ごとではなく部屋1つ分の統合された結果が得られたい。部屋全体を一度に把握したいから。
2. 住人として、部屋を一周撮った動画を渡したら、コマの切り出しを自動でやってもらいたい。写真を選んで撮り直す手間を省きたいから。
3. 住人として、ほぼ同じ構図のコマは自動で間引いてもらいたい。無駄なAPI費用を払いたくないから。
4. 住人として、1回の分析で使うコマ数の上限を指定したい。費用を自分で制御したいから。
5. 住人として、画像が見つからない、形式が対応外、動画が読めない、といった失敗の理由を日本語で明確に教えてもらいたい。何を直せばよいか分かるから。

**部屋の器(Room Shell)**

6. 住人として、部屋の幅・奥行き・天井高の推定値を、家具や物とは別の項目として見たい。器と中身を分けて考えたいから。
7. 住人として、寸法の推定値に確信度と「何を基準に推定したか」が添えられていてほしい。どのくらい信じてよいか判断したいから。
8. 住人として、実測した部屋の寸法を数値で指定して推定値を上書きしたい。推定が外れたときに配置もそれに合わせて直してほしいから。
9. 住人として、ドアと窓がどの壁のどの位置にあるかを知りたい。模様替えでそれらを塞がない案が欲しいから。

**部屋ツリー(Room Tree)**

10. 住人として、部屋の中の家具を、種類・おおよその大きさ・位置つきで一覧にしてほしい。何がどこにあるかを一目で把握したいから。
11. 住人として、小物(本、服、コップなど)が、それが載っている・入っている家具やエリアの下に階層化されていてほしい。フォルダを開くように部屋を辿りたいから。
12. 住人として、各ノードに「どの写真に写っていたか」が記録されていてほしい。AIの認識を写真で確かめたいから。
13. 住人として、各ノードに確信度が付いていてほしい。見直すべき項目を絞りたいから。
14. 住人として、複数の写真に写っていた同じ家具や物は1つに統合されていてほしい。重複した一覧では部屋の実態と合わないから。
15. 住人として、ツリーを実際のフォルダとファイルとして書き出してほしい。ファイルアプリやFinderでそのまま眺めたいから。
16. 住人として、AIが判別できなかった物や、自信がない場所を所見レポートで教えてほしい。追加で撮るべき場所が分かるから。

**配置と可視化**

17. 住人として、現在の配置を真上から見た2D間取り図として見たい。3Dがなくても部屋の全体像を確認したいから。
18. 住人として、間取り図に家具の名前が書かれていてほしい。図と一覧を対応づけたいから。

**模様替え(Rearrangement Proposal)**

19. 住人として、模様替え案を複数(件数指定)出してほしい。比べて選びたいから。
20. 住人として、「作業スペースを広く」「ベッドを窓から離す」のような目的を文章で伝えて、案に反映してほしい。自分の暮らし方に合う案が欲しいから。
21. 住人として、動かしたくない家具を指定して、その家具は全案で固定してほしい。動かせない物(据え付け、重量物)があるから。
22. 住人として、どの案も家具が部屋からはみ出さず、重なっていないことが保証されていてほしい。実行できない案を見せられたくないから。
23. 住人として、どの案もドアの開閉を妨げず、ドアから各家具へ人が通れる幅の通路があることを保証してほしい。生活できない配置は案ではないから。
24. 住人として、背の高い家具で窓を塞ぐ案は出してほしくない。採光と換気を失いたくないから。
25. 住人として、各案に「なぜこの配置がよいか」の理由が付いていてほしい。選ぶ根拠が欲しいから。
26. 住人として、各案に、今の配置から新しい配置へ移すための順序付きの移動手順が付いていてほしい。実際に動かす段取りが要るから。
27. 住人として、各案を2D間取り図として見たい。文章だけでは配置を想像しにくいから。
28. 住人として、検証に通らず捨てられた案があれば、その事実と理由を知りたい。AIが何を試して何に失敗したかを知りたいから。
29. 住人として、一度分析した部屋のデータを保存して、後日そのデータだけから模様替え案を作り直したい。写真を毎回送って費用と時間を払いたくないから。

**費用・プライバシー・運用**

30. 住人として、実行ごとに使ったトークン数と概算費用を表示してほしい。どこまで試せるか見通したいから。
31. 住人として、写真がAnthropicのAPI以外に送られないこと、出力は自分の指定したフォルダ以外に残らないことを保証してほしい。部屋の写真は個人情報だから。
32. 住人として、使うモデルを切り替えられるようにしてほしい。精度と費用のバランスを自分で選びたいから。
33. 住人として、APIキーがなくてもサンプルデータで動きを確かめられるモードがほしい。使い方を先に理解したいから。

**開発者**

34. 開発者として、VLMへの呼び出しを1つの境界(インターフェース)の裏に閉じ込めたい。テストでは偽物に差し替えて、残りの処理を決定的に検証したいから。
35. 開発者として、VLMの出力を必ずスキーマで検証し、不正ならその旨を伝えて再試行したい。壊れたJSONで後続処理を落としたくないから。
36. 開発者として、配置の妥当性検証(はみ出し・重なり・通路など)はVLMではなくコードで行いたい。VLMの出力を鵜呑みにせず、テストで固めたいから。
37. 開発者として、APIキーがあるときだけ動く実API疎通テストを1本持ちたい。偽物では確かめられない「本物の挙動」を定期的に見たいから。

## Implementation Decisions(実装上の決定)

### 全体方針

- 最初の形はCLIとPythonライブラリ。Web画面、iPhoneアプリ、3D表示は本仕様の範囲外(後述)。
- 実行環境はPython 3.12以上。パッケージ名は `room_agent`、コマンド名は `room-agent`。
- サブコマンドは `analyze`(取り込みと分析)、`propose`(模様替え案の生成)、`render`(保存済みデータから2D図を再生成)、`export-tree`(ツリーをフォルダとして書き出し)の4つ。
- すべての成果物は利用者が指定した出力フォルダに書く。それ以外の場所には何も残さない。ネットワーク送信はAnthropicのAPIのみ。

### 用語(ドメイン語彙)

本リポジトリに語彙集はまだないため、ここで定義する。コード・ドキュメント・出力ファイルで一貫して使う。

| 用語 | 英語名 | 意味 |
|---|---|---|
| 撮影セット | Capture | 1つの部屋を撮った入力一式。写真の集合、または動画から切り出したコマの集合。各コマにIDを振る |
| 部屋の器 | Room Shell | 部屋の幅・奥行き・天井高(メートル、推定値または利用者入力)と、開口部(ドア・窓)の一覧。中身とは独立 |
| 開口部 | Opening | ドアまたは窓。どの壁(北・東・南・西の相対表記)の、壁の端から何メートルの位置に、何メートルの幅であるか |
| 部屋ツリー | Room Tree | 部屋 → エリア → 家具 → 物、の階層。フォルダ構造に相当 |
| エリア | Zone | 部屋の中の意味的な区画(窓際、入口付近、デスク周り、ベッド周りなど)。VLMが命名する |
| 家具 | Furniture | 床に置かれ、配置替えの対象になるもの。種類(カテゴリ)、おおよその幅・奥行き・高さを持つ |
| 物 | Item | 家具の上・中・下、または床に置かれた小物。配置替えの対象ではなく、把握の対象 |
| 配置 | Layout | 器の上に敷いたグリッドにおける、各家具の占有範囲と向き |
| グリッド | Grid | 1マス0.25メートル。器の寸法から自動で縦横のマス数が決まる |
| 模様替え案 | Rearrangement Proposal | 同じ器・同じ家具に対する新しい配置と、理由、検証結果、移動手順 |
| 所見レポート | Findings Report | 分析でAIが分かったこと・分からなかったこと・確信度の低い項目をまとめた人向けの文書 |

### データモデル

- **Capture**: コマの一覧。各コマは、ID、元ファイル名、動画の場合は秒位置、送信用に縮小した画像を持つ。
- **Room Shell**: 幅・奥行き・天井高(それぞれ値、確信度、根拠の説明、出所が「推定」か「利用者入力」か)。開口部の一覧。
- **Room Tree のノード**: ID、種別(部屋/エリア/家具/物)、日本語の名前、カテゴリ(家具は定義済みの列挙。例: ベッド、机、椅子、棚、収納、ソファ、テーブル、テレビ台、その他)、おおよその寸法(不明なら空)、物の場合は親との関係(上に載る/中に入る/下にある/床に直置き)、写っていたコマのID一覧、確信度(0〜1)、補足。
- **Layout**: 家具IDごとに、左上のマス座標、幅と奥行きのマス数、向き(0/90/180/270度)。
- **Rearrangement Proposal**: ID、見出し、理由、配置、検証レポート(各ルールの合否と違反の説明)、移動手順(順序、家具ID、移動前の位置、移動後の位置、必要なら一時置き場の指示)、入力された目的と固定指定。
- **Room Model**(保存ファイル): 上記すべてと、使ったモデル名、トークン使用量、作成日時を1つにまとめたもの。`analyze` の出力であり、`propose` と `render` の入力。

### 取り込み(Ingest)

- 対応する静止画はJPEGとPNGとHEIC(HEICはJPEGに変換)。動画はffmpegが読める形式。
- 動画は毎秒1コマで切り出す。似たコマは知覚ハッシュ(dHash)のハミング距離で間引く。残ったコマが上限を超えるときは、時間軸に沿って均等に抜き取る。
- 1回の分析に送るコマ数の上限は既定で20。利用者が変更できる。上限を超える静止画セットも同じ均等抜き取りに従い、抜いた枚数を所見レポートに記す。
- 送信前にすべての画像を長辺1568ピクセル以下に縮小する。トークン効率と精度の釣り合いがよい大きさだからである。

### VLM呼び出し

- AnthropicのPython SDKを使う。モデルの既定は `claude-opus-5-5`。環境変数または引数で切り替えられる。
- 思考は適応型(パラメータは省略し、モデルの既定に従う)。分析の出力品質を優先し、努力度(effort)は `high` を明示する。
- 出力はJSONの構造化出力機能で受け取り、Pydanticのスキーマで検証する。アシスタント発話の先行入力(prefill)は使わない(現行モデルでは拒否される)。
- 長い出力に備え、ストリーミングで受けて最終メッセージを取り出す。
- 安全分類器による拒否(`stop_reason` が `refusal`)を必ず確認する。サーバー側フォールバックの既定設定を有効にして、拒否時に別モデルへ自動で回す。有効にしたことは実行ログに表示する。
- 1回の `analyze` では、すべてのコマを1つのリクエストに入れて、器・ツリー・配置を一度に生成させる。同じ物の重複解消はモデルに任せる。これが最も単純で、20コマ以内なら十分に収まる。
- 寸法推定では、モデルに基準物を使わせる(ドアの高さ約2.0メートル、天井高約2.4メートル、畳の約0.91×1.82メートル、A4用紙が写っていればそれ、など)。何を基準にしたかを根拠として出力させる。
- APIキーは `ANTHROPIC_API_KEY` または `ant auth login` のプロファイルから解決する(SDKの既定の解決順に従う)。

### VLMの境界(テストの継ぎ目)

- `VisionModel` という1つのインターフェースを定義する。操作は2つ。
  - 「部屋を分析する」: 撮影セットと補助情報(利用者が与えた寸法など)を受け取り、器・ツリー・配置の候補を返す。
  - 「配置案を出す」: 器、家具一覧(寸法つき)、開口部、固定指定、目的、前回の違反報告(あれば)を受け取り、配置案の候補を複数返す。
- 本番の実装はClaude APIを呼ぶ。テスト用の実装はあらかじめ用意した応答を返す。`--fake` 指定で切り替わる。
- このインターフェース以外の場所でAPIを呼ばない。

### 検証(コードで行う。VLMに任せない)

- スキーマ検証: VLMの出力は常にスキーマで検証する。不正なら、エラー内容を添えて最大2回再試行する。それでも不正なら失敗として報告する。
- 観測した配置(現在の配置)の検証: 家具がグリッドからはみ出していないか、重なっていないかを調べる。現在の配置については違反を「警告」として所見レポートに記録し、処理は続ける(写真の実態がそうなっている可能性があるため)。
- 模様替え案の検証(すべて満たさないと採用しない):
  1. 範囲内: すべての家具が器の中に収まる。
  2. 非重複: 家具同士の占有マスが重ならない。
  3. ドアの余白: ドアの正面、奥行き0.8メートル分のマスが空いている。
  4. 窓の確保: 高さ1.2メートルを超える家具が窓の正面のマスを占めない。
  5. 通路: ドアの前の空きマスから、各家具に隣接する空きマスへ、幅0.6メートル(3マス)以上の空き経路で到達できる(グリッド上の探索で判定)。
  6. 固定指定: 固定された家具の位置と向きが現在の配置と同一。
- 違反した案はVLMに違反内容を返して作り直させる。最大2回。それでも通らない案は「不採用」として理由つきで出力に残す。黙って捨てない。

### 移動手順の生成(決定的に計算する)

- 現在の配置と採用案の配置の差分から、位置が変わる家具を抽出する。
- 移動先が現在空いている家具から順に動かす。移動先が別の家具に占められていて順番で解けない循環があれば、1つを「部屋の中央の空き」に一時的に置く手順を挟んで解く。
- 手順は家具名・移動前・移動後の順序付きリストとして出力し、間取り図の座標と対応させる。

### 可視化と書き出し

- 2D間取り図: 真上から見たSVG。壁、ドア、窓、家具の矩形と名前、グリッドの目安線を描く。模様替え案は案ごとに1枚、現在の配置と並べて比較できるようにファイル名で対応づける。
- フォルダ書き出し: 部屋ツリーをそのままディレクトリ階層として書く。各ノードのディレクトリに、そのノードの情報(名前、カテゴリ、寸法、確信度、写っていたコマ)を1つの小さなJSONで置く。写真の切り抜きは行わない(VLMの位置指定が粗く、誤った切り抜きが混乱を招くため)。
- 所見レポート: Markdown。器の推定とその根拠、確信度の低いノードの一覧、重複統合の判断、見えなかった可能性のある領域、トークン使用量と概算費用を含む。

### 寸法の上書き

- 利用者が幅・奥行き(・天井高)を指定すると、器の出所を「利用者入力」に変え、グリッドの縦横を再計算し、各家具の占有範囲を比率で縮尺し直す。再分析は行わない。

### 費用の表示

- APIの応答に含まれる使用量を集計し、入力・出力トークン数と、モデルの単価から計算した概算金額を表示する。単価表は設定として持ち、更新できるようにする。

### 設定項目

- モデル名、コマ数の上限、案の件数、目的の文章、固定する家具、部屋の寸法、出力フォルダ、偽物モード。

## Testing Decisions(テストの方針)

- よいテストとは、外から見える振る舞いだけを検証するものである。生成されたファイルの有無と内容、JSONの値、検証器の合否、CLIの終了コードとメッセージを見る。内部の関数の呼び出し順や私的な状態は見ない。
- 継ぎ目は1つ。`VisionModel` インターフェースである。テストでは偽物に差し替え、VLM以外のすべてを決定的に検証する。偽物の応答は、実際のモデル出力を模した固定データとして用意する。
- 最上位のテストはCLIそのもの。偽物モードで `analyze` を実行し、Room Model、間取り図SVG、フォルダ書き出し、所見レポートが生成され、スキーマに合うことを確かめる。続けて `propose` を実行し、採用案と不採用案が検証レポートつきで出ることを確かめる。
- 純粋な処理には単体テストを置く。
  - コマ切り出しと間引き: ffmpegで色の変わる短い合成動画を作り、期待するコマ数が残ることを確かめる。
  - 配置の検証器: 手で作った配置に対し、6つのルールそれぞれの合否が期待どおりになることを確かめる(はみ出し、重なり、ドアの塞ぎ、窓の塞ぎ、通路の断絶、固定違反、そしてすべて合格の例)。
  - 移動手順の生成: 単純な入れ替え、循環がある入れ替えで、手順を順に適用すると採用案の配置に一致することを確かめる。
  - 2D図の描画: 出力SVGをXMLとして読み、家具の数と名前が配置に一致することを確かめる。
  - フォルダ書き出し: ツリーのノード数とディレクトリ数が一致することを確かめる。
  - 寸法の上書き: 上書き後のグリッド寸法と、家具の占有範囲の比率が保たれることを確かめる。
- 実API疎通テストを1本だけ置く。APIキーがない環境では自動で飛ばす。少数の写真を送り、スキーマに合う応答が返ることだけを確かめる(内容の正しさは検証しない。写真の中身に依存するため)。
- 先行事例: リポジトリは空のため、既存のテスト慣習はない。本仕様のテストがその最初の例になる。

## Out of Scope(範囲外)

- 3D表示(デフォルメ3Dを含む)。ただし本仕様の「器+配置」は、後から3Dを描くための入力になるよう設計する。
- iPhoneのRoomPlan(LiDAR)による間取り取り込み。
- iPhoneネイティブアプリ、Web画面。
- 片付けのタスク管理(散らかりの判定、やることリスト、進捗の追跡)。ただし「物」ノードはその土台になる。
- 複数の部屋、部屋をまたぐ移動。
- センチメートル単位の正確な寸法計測。本仕様の寸法はすべて推定値であり、利用者の上書きを前提とする。
- 模様替え後の部屋の写実的な画像生成。
- 時間をまたいだ同一物の追跡(昨日の本と今日の本が同じかどうか)。
- 写真の切り抜きやバウンディングボックスの出力。

## Further Notes(補足)

### 「どこまでできるか」についての正直な見通し

- できる見込みが高いこと: 家具の種類と一覧、どの壁際にあるかというおおまかな位置、小物のおおまかな一覧と「どの家具の上にあるか」、ドアと窓の有無と位置、物理的に成立する配置案の生成(検証器があるため)。
- 精度が限られること: 寸法。基準物があっても2〜3割の誤差は見込む。だから利用者の上書きを一級の機能にしている。
- 写真の質に左右されること: 小物の拾い漏れ(暗い、ぶれている、遠い)。所見レポートで「見えていない可能性がある領域」を伝え、撮り足しを促す。
- 1回の分析の費用の目安: 20コマで入力約3万トークン強。既定モデルの単価なら入力は数十円程度で、出力と思考を含めても1回あたり百数十円程度の見込み。実測して所見レポートに出す。

### 会話で決め、仕様に反映した判断

- 「メニュー」とは、目に映る空間から整理すべき物を列挙し、行動計画やタスク管理を行うことだと確認した。本仕様では「物」ノードの列挙と、模様替えの移動手順までを扱い、片付けのタスク管理は次の仕様に送る。
- 3Dは不要と確認した。代わりに「器+グリッド配置」という2Dの構造で室内空間を表す。
- 最初はCLIで作る。Web画面とiPhoneアプリの選択は、本仕様の結果を見て決める。

### 仕様作成者が利用者の代わりに決めた事項(異議があれば変更する)

- 実装言語はPython。理由は、画像・動画処理とAnthropic SDKの両方が揃っており、この環境で動作確認できること。
- 既定モデルは `claude-opus-5-5`。精度優先。費用を抑えたい場合は設定で切り替える。
- グリッドは1マス0.25メートル。家具の大きさの粒度と計算量の釣り合いから。
- コマ数の上限は既定20。1リクエストに収め、重複解消をモデルに任せるため。
- 通路幅0.6メートル、ドア前0.8メートル、窓を塞ぐ家具の高さ1.2メートル、という検証の閾値。一般的な住宅の目安から。すべて設定で変えられる。

### 次の仕様の候補

1. 片付けエージェント: 「物」ノードに「定位置か、散らかりか」の状態を持たせ、片付けタスクを生成し、再撮影で完了を確認する。
2. デフォルメ3D: 器と配置からローポリの部屋を描く。グリッドをそのまま使う。
3. iPhoneスキャン取り込み: RoomPlanの出力を器と配置に変換する。
4. Web画面: 写真のアップロードと結果の閲覧をブラウザで行う。
